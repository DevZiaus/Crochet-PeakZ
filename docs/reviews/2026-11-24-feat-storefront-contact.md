## Minor

### 🟡 Spec 0005 still documents the old first-entry client-IP rule, `docs/specs/0005-customer-auth/index.md:137`

**Problem**: The auth spec's value-sourcing table still reads "proxy overwrites `x-forwarded-for` with the socket peer; the API takes the **first** value only after the secret matches". `e9e933e` inverted exactly that: `getClientIp` now takes the **last** non-empty entry, and the web proxy forwards a single value rather than "the socket peer". The sync commit reconciled `scope.md`, spec 0003, and the `AGENTS.md` files but not the one spec that governs the changed code.
**Why it matters**: This is the file a future agent or `/sync` run trusts when touching `proxy-guard.ts` or the auth rate limiter. A stale "takes the first value" invites a revert to the spoofable behaviour that two reviews just closed, and the surrounding prose ("only after the secret matches") reads as authoritative.
**Suggested fix**: Update the row to state that the API reads the last non-empty `X-Forwarded-For` hop, that the web proxy forwards that single hop, and that deployments must keep exactly one trusted appending edge. Keep the `TRUST_PROXY`/proxy-secret clause that is still true.

### 🟡 The sync pass misattributes the hero logo, `apps/web/AGENTS.md:81` and `docs/specs/0003-design-system/index.md:63,132`

**Problem**: All three replacement sentences say `BrandLogo` renders `public/logo.webp` "across the header, footer, hero, auth layout, and admin sidebar". The hero does not use `BrandLogo`: `apps/web/src/app/(storefront)/page.tsx:129` renders a raw `next/image` of **`/logo-square.webp`** with a custom mask and blend classes. Only the header, footer, auth layout (`BrandLogo`) and admin sidebar (inline `Image`) use `logo.webp`.
**Why it matters**: These lines were added specifically to stop future agents from making wrong decisions about brand assets. "The hero uses `BrandLogo`/`logo.webp`" is the kind of statement that leads someone to delete `logo-square.webp` as unreferenced, or to expect a wordmark change to propagate to the hero.
**Suggested fix**: Split the sentence: `BrandLogo` (`logo.webp` + two-tone wordmark) in header, footer and auth layout; `AdminLayout` renders `logo.webp` inline; the home hero renders `logo-square.webp` directly. Apply the same correction in the spec's value-sourcing row and follow-up checkbox.

### 🟡 Last-hop keying silently collapses every bucket behind a CDN, `apps/api/src/presentation/auth/proxy-guard.ts:68-74`

**Problem**: The fix trades spoofability for hop sensitivity. With one appending edge the last entry is the client; with two (Cloudflare or any CDN in front of Caddy) the last entry is the CDN's own address, so every visitor shares one bucket: 5 contact submissions per 15 minutes and 5 registrations per hour **for the entire site**, with the surplus rejected with 429 and a `Retry-After`. `docs/deployment.md:83-91` now warns about this, but the only mitigation offered is "put a proxy in front when you want per client limits", which is not actionable for an operator whose CDN _is_ the proxy, and there is no configuration that expresses "trust two hops". `TRUST_PROXY` exists for Express but `getClientIp`/`readClientIp` ignore it.
**Why it matters**: A CDN-fronted deployment is a plausible, previously working shape. The failure mode is quiet — the store keeps serving, and customers simply stop being able to send messages once five people have — which is exactly the class of bug that costs a small shop real orders.
**Suggested fix**: Make the trusted hop count explicit (an env value, or reuse `TRUST_PROXY`) and have `getClientIp` and `readClientIp` select the entry at that depth, falling back to the current last-hop behaviour at the default of one. If that is deferred, promote the CDN caveat out of the paragraph into the quickstart steps with the concrete consequence (site-wide limits), so an operator does not discover it in production.

### 🟡 No end-to-end coverage for the contact path or the one-origin routing, `e2e/` (no contact spec)

**Problem**: `e2e/` contains `auth.spec.ts`, `catalog.spec.ts`, and `currency.spec.ts` only. The contact feature — the branch's headline — is covered by RTL component tests and by a mocked-fetch test of the Next proxy (`apps/web/src/app/api/contact/route.test.ts`), but nothing drives a real browser through a real web→API hop, and nothing asserts the form renders and is reachable from the header/footer/legal pages in the running app.
**Why it matters**: The two findings this branch has produced across three reviews — "the edge routes `/api/contact` straight to Express" and "the API keys on the spoofable header" — were both invisible to unit tests and only visible in the deployed topology. The project already gates on Playwright with axe-core; this is the one surface where the routing is the risk.
**Suggested fix**: Add a Playwright spec that loads `/contact`, submits a valid message against a stubbed or test-mode transport, asserts the success status, and runs the axe accessibility assertion on the page. A second case posting from a second "IP" header would pin the 429 copy end to end.

## Nits

- ⚪ `deploy/nginx.conf.example:31-41`, the `/api/` location has no `client_max_body_size`/20KB equivalent, so a 1MB body reaches Express and is buffered by `express.json` before the router's 413. The Caddyfile got the matching cap; mirror it here.
- ⚪ `docs/deployment.md:86-89`, "requests routed through the web proxy collapse every rate limit bucket … to one `unknown` client" is true for honest browsers only; when the port is exposed a crafted client can still supply its own `X-Forwarded-For`. Say "browsers" or "requests without forged headers" to keep the claim exact.
- ⚪ `apps/api/src/config/env.ts:250-253`, the warning fires only when `CONTACT_EMAIL` is exactly the default, so a `resend.dev` sender with any other unverified inbox still boots "healthy" and fails at send time. Consider warning on any `resend.dev` sender, mentioning the default inbox as the likely fix.
- ⚪ `apps/web/src/app/api/contact/route.ts:32-34` (carried over), `isSameOrigin` treats an absent `Origin` as same-origin; defense-in-depth only since the API re-checks, but prefer an explicit assertion.
- ⚪ `apps/web/src/app/api/contact/route.ts:124` (carried over), the proxy overwrites `origin` with `env.webAppUrl` upstream; fine today, note it for anyone adding per-client origin auditing.
- ⚪ `apps/web/src/app/(storefront)/page.tsx:129-135` (carried over), the hero's `mix-blend-multiply` logo-square treatment and absolutely-positioned badges deserve a visual pass in `/check verify`; the owner confirms the scroll-reveal fade is intended.

## Strengths

- The limiter rewrite is careful and, unusually, fully specified by its tests: amortized sweeping gated on `pruneIntervalMs` and only above the cap, `hits.delete`/`hits.set` on both the allowed and denied paths so LRU order means "last active" rather than "first seen", and an eviction test that pins the consequence (an evicted key gets a fresh window) instead of leaving it implicit.
- The IP fix is layered rather than single-point: last-hop parsing in the API, a matching `readClientIp`, an overwriting nginx example, a Caddy body cap, and a regression test that reproduces the exact spoof (three client addresses behind one edge address → 429 on the third). Each layer is documented at the point where the assumption lives.
- `getContactEmailStartupWarning` is the right shape for a config smell: pure, `Pick<>`-typed, exported with TSDoc, tested for the four interesting combinations, and called once from the composition root behind a `NODE_ENV !== "test"` guard rather than sprinkled into the send path.
- The contact feature still holds the architecture line: a zero-import domain entity, ports declared in `domain/`, a thin `submitContact` orchestrator that validates before consuming a slot and releases only its own id-bound slot, and an injectable Resend transport so tests assert the envelope rather than calling Resend.
- Documentation work is mostly surgical and honest — scope features 29 and 33 now record what shipped and what remains instead of flipping to done, and spec 0003's palette and logo sections were updated rather than rewritten.
