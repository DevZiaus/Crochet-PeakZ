## Minor

### 🟡 The Nginx Cloudflare section offers two mutually exclusive layouts, `deploy/nginx.conf.example:17-19,36`

**Problem**: The section recommends the realip path (keep `TRUST_PROXY=1` / `TRUSTED_PROXY_HOPS=1`) and offers, as "alternative without realip", switching `location = /api/contact` and `location /api/` back to `$proxy_add_x_forwarded_for` with `TRUST_PROXY=2` and `TRUSTED_PROXY_HOPS=2`. But `location /api/auth/` (line 36) and `location /` (line 73) keep appending to `X-Forwarded-For`, so under that alternative the chain the web server sees is `visitor, cloudflare-edge`, and `TRUSTED_PROXY_HOPS=2` on the web then selects the Cloudflare edge address while the API, at two hops, selects the visitor. The two sub layouts the file offers (recommended-for-web plus alternative-for-API, or alternative everywhere) do not both work: the two hop value is only correct when every location appends rather than overwrites.
**Why it matters**: The alternative exists precisely for hosts without the realip module. An operator who takes it follows the file literally and ends up with inconsistent visitor attribution across tiers (every web side per IP key — session reads, role fetches, the `ipAddress` stamped on auth rows — collapsed onto the edge IP, while the contact bucket stays per visitor), the exact failure class this branch has fixed twice, and has to discover the hop count interaction themselves.
**Suggested fix**: Make the section state one coherent story. If the realip module is unavailable, extend the alternative to all proxy locations (`/api/auth/` and `/` as well) and say the web tier then runs `TRUSTED_PROXY_HOPS=2` because every location appends; or drop the two hop value from the alternative and accept that without realip the web tier cannot recover the visitor from the header chain at all.

### 🟡 The relay's declared length 413 branch is untested, `apps/web/src/app/api/contact/route.ts:57-60`

**Problem**: `readLimitedBody` has two 413 paths: the early reject on a declared `Content-Length` above `CONTACT_MAX_BODY_BYTES`, and the cumulative cap inside the streaming read loop. The 413 test in `route.test.ts:68-81` builds a `NextRequest` from a body string, which exposes no `content-length` header (verified locally against the same request shape), so it exercises the read loop path only. The declared length branch — the one a production relay hits first, since real HTTP clients send the header — has no test.
**Why it matters**: The two branches guard the same contract but fail at different points. A future change that breaks one of them (comparing against the wrong constant, dropping the `Number.isFinite` guard, inverting the comparison) would pass the suite while the other branch still covers the test's path.
**Suggested fix**: Add one test that sets `content-length` above 20,000 (the body can be small or absent) and asserts 413 with `fetchMock` not called; the cross origin test already shows the pattern.

## Strengths

- The Caddy fix is honest about Caddy's behaviour instead of pretending a knob does more than it does: both the Caddyfile comment and the deployment doc state that `client_ip_headers` is not a substitute and why, and the hop counts are right on both tiers for every documented layout.
- The E2E transport invariant is enforced by construction rather than by a remembered note: the API `webServer` entry has `reuseExistingServer: false` with a comment that says why, the config header matches the behaviour, and the secretless relay shape the comment cites is now pinned by an assertion.
- The contact limiter is a well thought bounded design: idempotent per-slot release so a delivery failure refunds exactly one slot, an LRU bound at 10,000 keys with a throttled expired-key sweep, and tests that pin the hard cases (concurrent interleaving of releases, LRU freshness of actively denied keys, saturation at the default cap).
- The Facebook premise change is careful: the entity owns the link policy (`canLinkOAuthProvider`), the use case throws before any mutation, the callback maps the failure to `link_failed` without leaking internals or logging noise for the expected case, and the spec records the premise, the decision not to add a confirmation step, and an explicit before-launch verification follow-up.
- `x-proxy-client-ip` is wired into every web to API path (auth relay, session read, role fetch, cookie refresh, contact relay) and asserted at one hop and two hops, so intermediate router chains stop shifting rate limit keys.
