## Major

### 🟠 Contact rate-limit bucket is client-selectable when the edge routes `/api/contact` directly to the API, `apps/api/src/presentation/contact/contact.routes.ts:86`

**Problem**: The contact router keys its limiter on `getClientIp(req)`, which takes the **first** `X-Forwarded-For` entry (`apps/api/src/presentation/auth/proxy-guard.ts:65-67`), and the route is public — no proxy secret. In the documented one-origin deployments the browser's `POST /api/contact` never reaches the Next.js contact proxy: `deploy/Caddyfile:23-25` sends `/api/*` straight to `api:4000` (only `/api/auth/*` detours through web), `deploy/nginx.conf.example:31-39` does the same, and `docs/deployment.md:178-180` instructs it for bare metal. The web proxy's careful `readClientIp` sanitization (last hop = the edge-added address) is therefore bypassed on exactly the path the limiter relies on. The bundled Caddy is safe — modern Caddy replaces `X-Forwarded-For` with the peer IP for untrusted clients (verified against `reverseproxy.go` `addForwardedHeaders`) — but the bundled nginx example uses `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for` (line 36), which **preserves the client-supplied header** and appends `$remote_addr`. A script can send `X-Forwarded-For: <fresh random IP>` on every request and get a fresh bucket each time.

**Why it matters**: The per-IP 5-per-15-minutes limit is the only hard anti-spam boundary on this endpoint — the honeypot, fill-time, and link-count guards are client-supplied deterrents that a script satisfies trivially (as the shared schema's own comment acknowledges). Bypassing the limiter under the documented nginx configuration allows unlimited contact deliveries: flooding the store inbox, burning Resend quota/cost, and damaging sender reputation. Auth routes are unaffected (they require the proxy secret and ride the web proxy's single sanitized value). Related: the no-edge "every bucket collapses to `unknown`" limitation documented for auth at `docs/deployment.md:85-88` now also applies to contact — without an edge, all honest visitors share one global 5-per-15-minutes bucket, and a client can rotate `X-Real-IP` through the web proxy's fallback.

**Suggested fix**: Make the contact key unspoofable on every documented path. Options: (a) take the **last** `X-Forwarded-For` entry in `getClientIp` — the web proxy sends a single value so first == last there, and appending edges put the real client last; (b) route `/api/contact` through the Next.js proxy at the edge, like `/api/auth/*`; or (c) set `X-Forwarded-For` to `$remote_addr` in the nginx `/api/` location. Add a regression test posting a multi-entry XFF chain and asserting the bucket is the edge-added address, update `docs/deployment.md` to cover contact explicitly (including the no-edge collapse), and consider a 20KB `request_body max_size` on the Caddy `/api/*` handle to match the web proxy's cap.

## Minor

### 🟡 Rate limiter scans the entire key map on every consume past 10,000 keys, `apps/api/src/presentation/contact/contact-rate-limit.ts:63-69`

**Problem**: Once `hits.size > PRUNE_THRESHOLD` (10,000), every `consume` iterates the whole map to prune fully-expired keys. Under the key-rotation attack above, an attacker grows the map to hundreds of thousands of live keys and forces an O(n) scan per request — CPU amplification stacked on the limiter bypass. Even without abuse, a burst of 10k+ unique IPs inside one window makes every subsequent submission pay a full-map scan.
**Why it matters**: A public, unauthenticated endpoint should not do work proportional to total recent traffic per request; this is a cheap DoS lever and will also bite organic traffic spikes.
**Suggested fix**: Amortize pruning — sweep on a time budget (e.g. at most once per second), track a global next-expiry, or prune incrementally — and/or cap the map size. Add a test exercising behavior past the threshold.

### 🟡 Facebook first sign-in still creates an account from any returned email; the unconfirmed-email premise is now load-bearing for new accounts, `apps/api/src/application/use-cases/oauth.ts:37-48`

**Problem**: The link gate closes the takeover class, but a first Facebook sign-in still creates an account marked `emailVerified: true` from whatever address Graph returns. If the premise ever breaks (Graph returning an unconfirmed address), an attacker could squat a victim's not-yet-registered email, blocking the victim's local registration; and because Google may later link that account while the stored provider stays `FACEBOOK` (`oauth.ts:70-82`), the original Facebook identity would retain access even after the victim "reclaims" the account via Google. Spec 0005 records the premise ("omits `email` when no valid primary address is available"), which matches Meta's wording but is not a verification attestation.
**Why it matters**: Low probability, but the blast radius is a persistent shared-access account rather than a one-off spam event; the previous review's option (b) suggested gating the new-account path too, and only the link path was gated.
**Suggested fix**: Record a deliberate confirmation of the premise in spec 0005 (real-account check or Meta documentation citation), and consider either an independent confirmation step before a Facebook-created account is marked verified, or revisiting provider retention when Google links a `FACEBOOK` account. Not blocking: no existing account can be touched, and the policy is documented.

### 🟡 Durable knowledge not reconciled with what shipped, `docs/scope/scope.md:46` (and `docs/specs/0003-design-system/index.md:63,132`, `apps/web/AGENTS.md:79`)

**Problem**: Three canonical documents now contradict the code: (1) scope feature 33 "Rate limiting & abuse protection" is still `planned / needs a decision` although this branch ships exactly the application-level contact limiter the feature describes as its fallback (and feature 29's legal pages partially shipped via privacy/data-deletion); (2) spec 0003 still says the header renders a text wordmark placeholder until a `public/logo.svg` exists, while `BrandLogo` ships with `/logo.webp`; (3) `apps/web/AGENTS.md:79` claims "The current storefront does not reference them" about the logo files, which the header, footer, auth layout, admin sidebar, and hero now all reference.
**Why it matters**: These are the files future agents and `/scope`/`/sync` runs trust; stale claims invite wrong decisions (e.g., re-designing the contact limiter from scratch, or "cleaning up" referenced assets).
**Suggested fix**: A surgical `/sync` pass: note the shipped contact limiter under feature 33 (and the partial legal pages under 29), update spec 0003's logo sourcing line and follow-up, and correct the brand-assets sentence.

### 🟡 Default configuration cannot deliver contact mail in Resend test mode, and startup gives no hint, `apps/api/src/config/env.ts:250-272`

**Problem**: With the example `EMAIL_FROM=Crochet PeakZ <onboarding@resend.dev>` (`.env.docker.example:52`) and the default `CONTACT_EMAIL=hello@crochetpeakz.tech`, Resend test mode rejects the send (403 `validation_error`) and every visitor sees the friendly 502. The failure is handled correctly in code (slot released, no internals leaked) and is documented in `docs/deployment.md`'s Contact form section and the owner's environment note — but `loadEnv` validates only shape, so a fresh deployment boots "healthy" with a silently broken feature.
**Why it matters**: The out-of-the-box experience of the flagship self-host path is a contact form that never delivers until an operator discovers the env var; the owner's note explicitly flags this as worth acting on before launch.
**Suggested fix**: Log a startup warning when `EMAIL_FROM` is a `resend.dev` onboarding address while `CONTACT_EMAIL` is left at the default (or surface the required override in the quickstart steps, not only the reference table). Configuration guidance, not a code fault — hence Minor.
