# Review, feat/storefront-contact, 2026-11-22

**Reviewed by**: Qwen3.8-27B (author on a different model, per `/check review`)
**Scope**: 84 files, branch vs merge base `1a3699f9` (currency switcher already on main; this branch is the contact feature, static pages, brand/logo, palette, and a few auth/OAuth tweaks)
**Verdict**: Changes requested

## Summary

The contact feature is a genuinely clean end-to-end tracer bullet: a shared Zod contract, a pure and well-tested domain anti-spam entity, an injectable Resend adapter, a fixed-window rate limiter with slot rollback, and a Next.js proxy that enforces same-origin and a body cap before touching the API. Clean Architecture held up, every new surface has real tests, and `npm run typecheck` plus all three suites pass locally (API 282, web 479, shared 85). Two issues keep this from a clean approve: the "CrocheT" (capital-T) brand spelling, which existed only in the webmanifest at the merge base and was propagated by this branch into page titles, JSON-LD, and the subject lines of customer-facing auth and contact emails; and a Facebook OAuth change that drops the email-verification check on a premise the Graph API does not actually guarantee, which reintroduces an account-takeover path the original code was written to prevent.

## Major

### 🟠 Facebook OAuth accepts any non-empty email on an unguaranteed premise — reintroduces account-takeover / link-hijack, `apps/api/src/presentation/auth/auth.routes.ts:483-489`

**Problem**: The branch removes Facebook's `verified` profile field and now treats _any_ non-empty Facebook email as proven (`if (provider === "google" && profile._json?.email_verified !== true)` — the guard no longer applies to Facebook). The justification in the code comment, spec 0005 AC-8, and `docs/specs/0005`'s security model is that "Facebook's Graph API deprecated `verified` and only exposes a user's confirmed primary address in `email`, so any non-empty Facebook email is accepted." That premise is not what Meta documents. The current Graph API reference for `User.email` reads: "The User's primary email address listed on their profile. This field will not be returned if no valid email address is available." "Primary … listed on their profile" is not "confirmed/verified." The deprecated `verified` field measured _account_ verification (SMS/credit-card), which is indeed unrelated to email — but the original code used it as a proxy for "the provider is willing to assert this address is the user's real one." By dropping it entirely, identity now rests solely on Facebook returning _some_ email, which the API does not explicitly promise is a verified/confirmed address.

**Why it matters**: Email is the account identity key. If Facebook can ever return an address the user has not confirmed (or, in edge cases, a secondary/legacy profile address), an attacker who signs in with Facebook on their own device and supplies a _victim's_ email would be resolved/linked to the victim's existing account, marked `emailVerified: true`, and signed in as them. That is exactly the takeover class the M1/"unproven email is refused" invariant was designed to block, and it is the class the original `verified` check guarded. The branch even goes out of its way to _enable_ `appsecret_proof` on the Facebook profile request (a hardening step), which makes the simultaneous weakening of email verification a clear net-negative on the security axis.

**Suggested fix**: Verify the actual behavior before relying on it — confirm against a real Facebook account (or Meta's docs / `appsecret_proof` response) that `email` is only ever returned for a _confirmed_ primary address, and record that confirmation in spec 0005. If it cannot be guaranteed, do not weaken the invariant: either (a) keep a per-provider verification attestation (e.g. require Facebook's OAuth `email` permission to be a confirmed address and surface that signal), or (b) treat a first Facebook sign-in whose email matches an _existing, previously-verified_ account as a link but gate the new-account path so a Facebook email can never auto-create/take-over an account without an independent verification step. At minimum, add a regression test capturing the intended "Facebook email is treated as verified" behavior and a spec line that pins the premise, so a future API change doesn't silently break the assumption.

### 🟠 Brand mis-spelled "CrocheT" propagated to every user-facing surface, incl. customer emails, `apps/web/public/site.webmanifest:2` (76 occurrences)

**Problem**: At the merge base the string "CrocheT" (capital T) appeared in exactly one place — `site.webmanifest` — and the prior review (`docs/reviews/2026-11-16-feat-product-catalog-storefront.md`, Nits) already flagged that exact spelling as wrong ("brand name spelled 'CrocheT PeakZ' (capital T) unlike every other surface"). The correct brand, used consistently across the whole repo history, is "Crochet" (lowercase t). This branch took the misspelling and propagated it into ~70 additional locations: the site `<title>`/metadata template (`apps/web/src/app/layout.tsx:22-23`), every auth page meta description, the header/footer home-link `aria-label`s and copyright, all storefront page metadata + OG `alt` text, `design.md`, the landing hero, the new About/Contact/Privacy/Data-Deletion copy, the JSON-LD `Brand` name (`apps/web/src/lib/catalog/json-ld.ts:68`), the **subject and body of the verification and password-reset emails** (`apps/api/src/infrastructure/email/auth-email-templates.ts:41,50,52`), the **contact-notification email subject and text** (`apps/api/src/infrastructure/email/contact-email-template.ts:83,105`), the API startup log (`apps/api/src/index.ts:168`), env error strings and test fixtures, and `design.md`. The new tests even assert the misspelling (e.g. `expect(email.html).toContain("CrocheT")`), locking it in.

**Why it matters**: This ships to customers. The brand is wrong in the page title users see in the tab/bookmarks, in SEO-visible JSON-LD and OG tags, and — most visibly — in the text of every email the store sends (verification, password reset, and now contact). A brand misspelling in outbound email undermines trust and looks broken on first touch. It is not a behavior bug, so it is not a blocker, but it is a user-facing correctness defect introduced (widened) by this change.

**Suggested fix**: Decide the canonical spelling with the owner (all evidence points to "Crochet"), then do a single repo-wide correction of the wordmark string and update the test assertions that pin it. Do a deliberate sweep of `CrocheT` → `Crochet` in user-facing copy, metadata, email templates, and `design.md`, and re-run the suites. Keep `site.webmanifest` in the same pass so it stops diverging from the layout title (the prior nit also noted its `-` vs `—`).

## Minor

### 🟡 `submitContact` use case is dead code — the route re-implements its orchestration, `apps/api/src/application/contact/submit-contact.ts:49-54`

The application-layer `submitContact(dependencies, rawInput)` is exported and has a JSDoc contract, but nothing calls it — the router (`contact.routes.ts:82-104`) inlines the identical validate→consume-rate-limit→`sendContactMessage`→release-on-failure flow instead. The only used application export is `validateContactSubmission`. Having the "use case" (the object the architecture rules say should orchestrate) be un-reachable, with its delivery + rate-limit policy duplicated in presentation, is the kind of drift that lets the two copies diverge. Either have the router delegate to `submitContact` (moving the rate-limit consume/release into the use case or passing the limiter in) or delete the dead function.

### 🟡 Rate-limiter `release` can double-free on concurrent failures, `apps/api/src/presentation/contact/contact-rate-limit.ts:70-82`

`release(key)` unconditionally `pop()`s the most recent timestamp for the key. Two requests from the same IP that both fail delivery concurrently each call `release`, so two _different_ slots are removed — a spammer who can force failed deliveries (e.g. transiently overloading Resend, or a poison address) can drain the window faster than real submissions arrive and then exceed `max`. It is in-memory, per-process, and best-effort anti-spam, so this is not a hard limit, but the rollback that makes 502-friendly delivery safe has an off-by-N under concurrency. Track which timestamp a request consumed (e.g. store an index/nonce per consume) and remove that specific entry on release, or serialize consumption per key.

### 🟡 API body-size check uses re-serialized bytes, so it can both miss and false-positivize, `apps/api/src/presentation/contact/contact.routes.ts:60-68`

`bodyBytes = Buffer.byteLength(JSON.stringify(req.body ?? null))` measures the _re-serialized_ parsed object, not the raw request bytes. For a large Unicode-heavy payload the re-serialized form can be smaller than what was sent (under-estimating), and for any body with redundant spacing it can differ from the wire. The `content-length` check above it is the real bound, but the second condition is misleading as a "bytes" check and, because `express.json` already parses before the handler runs, `req.body` here is post-parse anyway. Compare the raw incoming length (the existing `declaredLength`) or a `content-length`-only check and drop the re-serialization, or document that it is an approximation.

### 🟡 `elapsedMs` / `website` are client-supplied with benign defaults — anti-spam is trivially satisfied by a crafted client, `packages/shared/src/contact/index.ts:80-83`

`elapsedMs: z.number().default(0)` and `website: z.string().default("")` mean a non-browser client (or a script) can send `elapsedMs: 99999` and an empty honeypot and pass both domain guards; the only real remaining gates are the link count and the rate limit. That is the usual trade-off for client-side anti-spam and is fine for the feature's purpose, but it is worth a one-line note (comment or spec) that these are _deterrents_, not authentication, so a future reader doesn't assume the fill-time check is a strong bot control.

### 🟡 `DEFAULT_CONTACT_EMAIL` is the single source for three consumers and can diverge from the API's `CONTACT_EMAIL`, `packages/shared/src/contact/index.ts:4`

`DEFAULT_CONTACT_EMAIL` (`hello@crochetpeakz.tech`) is the API's startup default (`apps/api/src/config/env.ts:256`), the mailto on the Contact/Privacy/Data-Deletion pages, and the `og`/copy. If an operator sets `CONTACT_EMAIL` to a different real inbox (the owner's notes confirm the Resend account is in test mode and they had to point `CONTACT_EMAIL` at a different address to make delivery work), the pages and mailto links still advertise the hardcoded default, so the address a customer clicks is not necessarily where their message lands. Keep the constant as the single declared default and, if the inbox can actually vary per deployment, surface the real destination (or document that the page mailto is intentionally a public handle separate from the routing inbox).

### 🟡 Contact form keeps a stale `elapsedMs` until successful submit; a slow failed submit can be rejected as "too fast", `apps/web/src/components/contact-form.tsx:99-100,184`

`elapsedMs` is computed from `loadedAtRef`, which is only reset to `Date.now()` on a _successful_ submit (line 184). If a user waits, submits, and the send fails (429/502), the fields are preserved but `loadedAt` is not advanced; a quick retry now measures from the original page load. That is correct in spirit (they didn't re-fill the form), but because the failure path can also _clear_ the form on a 200 and the fill-time floor is 3s, a fast re-submit after a failed attempt is more likely to trip `SUBMITTED_TOO_FAST` than the message implies. Consider resetting `loadedAtRef` after any completed round-trip (success or failure) so the timer tracks the last visible state of the form, or at least document the intent.

## Nits

- ⚪ `apps/web/src/app/api/contact/route.ts:32-34`, `isSameOrigin` returns `true` when no `Origin` header is present. Same-origin browsers always send `Origin` for a cross-site POST, but a raw client (curl) can omit it to bypass this check; the API re-enforces its own origin allowlist and `sec-fetch-site`, so it is defense-in-depth rather than the sole gate — still, prefer an explicit same-origin assertion over "absent ⇒ same origin."
- ⚪ `apps/web/src/app/api/contact/route.ts:124`, the proxy unconditionally sets `origin` to `env.webAppUrl` on the upstream call. That is what makes the API's allowlist pass, but it also means the API sees the web origin rather than the true browser origin; fine today, but note it for anyone adding per-client origin auditing.
- ⚪ `apps/web/src/app/(storefront)/page.tsx` hero, the `mix-blend-multiply dark:mix-blend-normal` logo treatment and the absolutely-positioned badges are hard to sanity-check without a screenshot; the owner's notes flag the reveal animation as intended, but the blend/overlay stack is worth a visual pass in `/check verify`.
- ⚪ `apps/api/src/presentation/contact/contact.routes.ts:88-95`, the 429 message is built with an inline ternary for pluralization; a small helper would read more clearly and is consistent with the rest of the codebase's label helpers.

## Strengths

- Clean Architecture held end to end: `contact-message.ts` is a pure, zero-import domain entity whose invariants (honeypot, fill-time, link count) are exhaustively unit-tested including `NaN`/`Infinity` fill-time; the application layer orchestrates through a `ContactEmailSender` port; the Resend adapter is injectable so tests assert the exact envelope handed to transport — exactly the isolation the project's test rules require (no live Resend/Google/Facebook).
- The rate limiter's consume-then-rollback-on-failure design is thoughtful and _tested_ (`contact.routes.test.ts` proves a 502 releases its slot so a retry still succeeds before the next one 429s), and `Retry-After` is surfaced end to end through the web proxy (`route.test.ts` relays the header).
- The web→API proxy is well-secured: same-origin + `sec-fetch-site` + content-type + a true streaming 20KB body cap (`readLimitedBody` cancels the reader on overflow) + a 10s `AbortSignal.timeout` before it ever reaches the API, and the API independently re-validates and re-enforces origin and rate limits — no single layer is the sole gate.
- Email composition is defensive: `escapeHtml` on every interpolated field, `\r\n`-stripped subject, a deterministic sub-256-char idempotency key, and a `Reply-To` set to the customer's address; the escape behavior is locked by a test that feeds `<script>` and asserts it is escaped in HTML and plain in text.
- The new static pages are consistent and accessible: single `h1`, canonical + OG metadata, and the contact page's `?topic=` preselection with an `isContactTopic` fallback — all covered by `static-pages.test.tsx`, including the invalid-topic fallback.
- The OAuth test updates are honest: they replace the now-removed "unverified Facebook" case with a real "no email returned ⇒ `email_missing`" case and add an explicit "Google `email_verified:false` ⇒ refused" case, and assert the new `appsecret_proof`/field-list on the Facebook profile request.

## Test coverage

Coverage of the new behavior is strong and I ran the full gates (typecheck clean; API 282 / web 479 / shared 85 passing). Covered: the shared contact schema (trim, every 400 class, `__proto__` guard), the domain entity (all three rejection codes + boundary links + `NaN`/`Infinity`), the Resend adapter (envelope passthrough, API-error and thrown-transport → `ContactDeliveryError`), the contact router over a real HTTP server (200, 415, 413, 403 cross-site/bad-origin, 400 field/honeypot/too-fast/links, and the full rate-limit-then-429-with-rollback sequence), the web proxy (403/415/413/200/429-relay/502), the `ContactForm` component (accessible fields, honeypot hidden from AT, inline validation, success reset, 429 message, `initialTopic`), and the four static pages (h1, canonical, links, topic preselect/fallback). Also covered: skip-link tests for auth and admin layouts, the vertical OAuth buttons, the pill button variants, the new `/blog` "Meet the maker"/"Start a custom order" links, and the Facebook profile-request field/`appsecret_proof` assertion.

Gaps worth closing: (1) the Facebook-email-trusted-as-verified behavior is asserted only in the negative "no email" case — there is no test pinning the intended "non-empty Facebook email is accepted as verified" decision that the Major above depends on; (2) the `submitContact` use case is untested _and_ unused, which is the smell; (3) the rate-limiter `release` concurrency/double-free case is untested (the existing test is a single-threaded sequential path).
